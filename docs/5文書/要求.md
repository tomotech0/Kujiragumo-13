# 要求 — Giftia 送別ギフトの「決めきれない」を解決する

前提: 講座（Tech0 Step3-1）の Giftia ケースで、モック（Next.js＋FastAPI＋班の Azure MySQL）を作る。2026-11-17（火）の週までは手元のパソコンで動かし、その後 Azure にデプロイする予定（ADR-0009）。決済・ログインは対象外。
今回の開発①で実装するのは BR-02・BR-03（1位と理由の表示。ADR-0012）と BR-04（の計測）。BR-01 は今の検索画面をそのまま使い、新しくは作らない（ADR-0008）。
元にした書類：班の「要求定義書」（v20、2026-11-21 更新版。班の Google Drive）。数字の出典はケース資料の Exhibit 番号か、班の DB の表の名前で書く。

## 誰が使うか
<!-- 利用者の立場・人数・利用場面 -->

- **贈る人**（顧客A）：職場の先輩（40代女性）が異動するので、同僚3人で 4,500円前後の送別の品を贈りたい。先輩とはあまり親しくなく、好みはよく知らない（要求定義書 3.1 候補1）
- **一緒に贈る同僚**（2人）：贈る人から相談を受け、候補を見て意見を返す

## 何に困っているか
<!-- 今の困りごと。できれば具体的な場面で -->

好みをよく知らない先輩への送別の品で「変なものを選んだ」と思われたくないのに、何なら変じゃないのか確信が持てず、その責任を自分ひとりで負いたくないので、候補を絞っても最後を決めきれない（のではないか）。（要求定義書 3.2）

- 「40代 女性 送別 プレゼント」で検索したが、絞れなかった（要求定義書 3.1）
- 送別シーンの購入率は 1.7% で、5つのシーンの中で最も低い（Exhibit 1 表2）

## できると嬉しいこと

施策の目的（要求定義書 1章）
- 送別シーンで、ギフトを選びきれない人が、同僚の賛同と外さない根拠を得て、後で理由を説明できる形で決められるようにする。その結果、送別シーンの注文件数を、ほかのシーンより伸ばす

提供価値（要求定義書 4.1）
- 選んだ理由を、あとで聞かれても説明できる状態で買える
- これを選んでいいのかという確認を、周りの人と一緒にできる

要求（要求定義書 4.2）

| 要求ID | 要求 | 優先度 |
| --- | --- | --- |
| BR-01 | 好みをよく知らない相手でも、相手との関係や予算を手がかりに、候補を数個まで絞れる | 中 |
| BR-02 | 一緒に贈る人の賛成を集めて、自分ひとりの判断にせず決められる | 高 |
| BR-03 | 選んだ理由を、あとで「なんでこれにしたの？」と聞かれても説明できる状態で決められる | 高 |
| BR-04 | 送別シーンで、候補を決めるまでの迷いを減らし、送別の注文件数の伸び（前年同月比）を、ほかの4シーンの伸びより大きくする | 高 |

- BR-03 は、提供価値の1つめ「選んだ理由を、あとで聞かれても説明できる状態で買える」に対応する。「変なものと思われない」は相手が決める評価で、行動では確かめにくいため、要求から外した（要求定義書 7章 4〜5週目）
- BR-04 の根拠：送別は、購入率 1.7% が5シーンで最も低く、平均閲覧商品数 16.5 が最も多く、購入までの日数 5.3日が最も長い（Exhibit 1 表2）。迷いが多いので、迷いを減らせば注文件数が伸びるのではないか（仮説）
- BR-04 の見る数字を、購入率から注文件数の伸びに変えた（要求定義書 更新履歴 2026-11-21）。送別は季節で注文件数が大きく動く（3月に約30%、2〜4月に約51%。班の DB の `orders` 表、2025-07〜2026-06）ため、前年の同じ月と比べ、さらにほかの4シーンの伸びと比べる

## 成功の定義
<!-- 何がどうなれば成功と言えるか -->

要求定義書 6章から。

- Phase1（このモック）：他班など3人1組（5組ほど。Aさんと同じような属性で絞る）に一連の機能を使ってもらい、スムーズに決められたか、購入したくなったかを聞き取る。もしくは、一部のアカウントだけ機能を変えて、数字で比べる
  - 指標①：共有URLを受け取った同僚の**投票率**（賛成を送った人の割合。分母は下の「未決」の最後の行）
    - 成功：80% 以上（今の LINE 相談では、同僚2人とも賛成を返した。新しい機能もこれに近い反応がないと、LINE から乗り換える理由がない。要求定義書 4.3）
    - 仮説が間違い：50% 以下
  - 指標②：機能を使った組のうち、1位を1つに決めて「カートに入れる」（このモックでは購入ボタン。AC-04）を押した組の数
    - 成功：5組中4組以上
    - 仮説が間違い：5組中2組以下
- Phase2（本番を想定）：実装後3か月（送別は季節で注文件数が動くので、2〜4月）の、送別シーンの注文件数の前年同月比を、ほかの4シーンの前年同月比と比べる。数えるのは班の DB の `orders` 表（注文日と推定シーンで月ごとに数え、3か月を足す）
  - 成功：「送別の伸び率 − ほかの4シーンの伸び率」が **+6ポイント以上**
    - 何もしなかった年（2025年→2026年の2〜4月）でも、差は +2.0ポイントあった（送別 +8.5%、ほかの4シーン +6.4%。班の DB）。注文件数による偶然のぶれは片側で約3.2ポイント。2.0＋3.2≒5.2 なので、+6 を超えれば偶然とは言いにくい
    - +6ポイントは、年に約880件・約460万円（約14,700件 × 6% × 5,200円）
  - 仮説が間違い：差が +2ポイント未満で、しかも送別の注文の2割以上が共有リストを通っていたとき（「迷った人が Giftia の中で決めきれれば、送別の注文が増える」という仮説は間違いと判断する）
    - 差が +2ポイント未満で、共有リストを通った注文が2割未満のとき：仮説は試せていない（使われなかった問題として、別に考える）
    - 差が +2〜+6ポイントのとき：判定できない。一部のアカウントだけ機能を変えて比べる
    - 2割にした理由：2割の組で使われ、使った組の注文が30%増えれば、+6 に届く
  - 共有リストを通った注文は、`orders` 表に共有リストの番号（`share_id`）を残して数える。ほかの4シーンの伸びは、共有リストを通った注文を除いて数える（開発①では作らない。Phase2 で検討）
  - 注意：シーンは、Giftia の分析部門が注文ごとに2つの手がかり（購入時に客が選んだギフトの用途タグ、検索キーワード）から推定したもの。推定であることに留意する
