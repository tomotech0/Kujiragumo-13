### デプロイを見込んだ書き方（ADR-0009）

来週デプロイしたときに直さずに済むよう、今週から次のように書く。

| デプロイで変わるもの | 書き方 |
| --- | --- |
| 画面から呼ぶ API の URL | `lib/config.ts` の値（環境変数 `NEXT_PUBLIC_API_URL`。なければ `http://localhost:8000`）を使う。各ファイルに `localhost` を書かない |

| API を呼んでよい画面の URL（CORS） | 今のまま `.env` の `CORS_ORIGINS`。デプロイ先の画面の URL は、デプロイのときに足す |
| DB の接続情報 | 今のまま `.env`。デプロイ先では Azure の設定画面の環境変数に入れる（Git に入れない） |
| ライブラリの版 | `requirements.txt` は `==` で固定（ADR-0002）。新しいライブラリを足すときは班に知らせる |

## データ

仕様「データ」の5つの表を `backend/sql/001_share_tables.sql` で作る（ADR-0010）。

- `CREATE TABLE IF NOT EXISTS` だけを書く。`DROP`・`ALTER`・既存の表への `INSERT`・`UPDATE`・`DELETE` は書かない（N-02）
- 外部キーは付けない（既存の `products` 表に影響を出さないため）。`product_id` が `products` にあるかは API で確かめる
- 文字コードは既存の表と同じ（`utf8mb4`）
- 実行するのは C だけ。実行したら、PR に「実行した日時」と `SHOW TABLES` の結果を書く（接続先は書かない）

## 処理の流れ

1. ①② 画面が `GET /api/search` を呼ぶ（今のまま）→ ② で商品の「候補に入れる」を押すと、画面の中で選んだ商品の ID を3つまで覚える（F-03）
2. ② で「共有リストを作る」→ `POST /api/shares` → `routers/shares.py` が UUID を作り、`share_lists`・`share_items` に書く → ③ の画面へ移る（F-03）
3. ④ 同僚が共有URLを開く → `GET /api/shares/{share_id}`（A の `routers/shares.py`）で候補を読む → 「送る」で `POST /api/shares/{share_id}/answers` → `routers/colleague.py` が、賛成した候補に理由があるか（`backend/reasons.py` の key か）を確かめ、`answer_id`（UUID）を1つ作り、`votes`（0〜3行）・`comments`（0〜3行）にその番号つきで書く。名前は受け取らない（F-04、ADR-0010・0013・0014）
4. ⑤ 贈る人が開く → `GET /api/shares/{share_id}/summary` が、候補ごとに「点数＝賛成の数×5＋理由の重みの合計」（重みは `backend/reasons.py`）を出し、点数 → `products.rating` → `share_items.position` の順に並べて、1位と理由を返す。賛成数・点数は返さない → 購入ボタンで `POST /api/shares/{share_id}/purchase-click` → `purchase_clicks` に書く（F-06・F-07・F-08、ADR-0012）

DB に書くときは `database.py` の `execute(query, params)`（1つ書く）か、まとめて確定するときは `execute_all(statements)` を使う。値は必ず `%s` で渡す（N-03）。
