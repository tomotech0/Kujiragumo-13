### PRのレビューとマージ
- **自分のPRは自分でマージしない。** PMのPRも例外にしない
- PMのPRは、他のメンバーのいずれかがレビューし、**レビューした本人がマージする**
- メンバーのPRはPMがレビュー・マージする（内容が自分の担当領域に近い場合は相互レビュー）
- レビュー観点は「文書に無い機能を作っていないか」「証拠（テスト結果・スクショ）が付いているか」の2点。
  ADR.mdに差分があるPRでは3点目として「下流の文書にも落ちているか」を見る（後述「ADRを足したときの手順」）

### AIエージェントの利用
全員がClaude Code等のエージェントを使ってよい。ただし人間と同じルールを適用する。
- 文書に無い機能は作らせない。気づいたら止めてPMへ返し、ADRを切ってから作る
- 生成させたコードもレビューとPRを通す。証拠なき完了報告は受け取らない

## リスクと撤退ライン

| リスク | 兆候 | 撤退ライン |
| --- | --- | --- |
| デプロイ先だけ動かない | 手元では動くのに、デプロイ先で画面が API につながらない | `localhost` を直接書いた箇所と、CORS の許可先（`CORS_ORIGINS`）にデプロイ先の画面の URL があるかを見る。発表に間に合わなければ手元で発表する |
| C-0 が遅れて、B・C が保存を試せない | C-0 の PR が出ない | B・C は画面だけ先に作り、保存は C-0 の merge 後につなぐ |
| 同じファイルを書き換えてぶつかる | merge のときにコンフリクトが出る | 設計.md「構成」の担当外のファイルは触らない。ぶつかったら自分で直さず、PM に相談する |
| 班のDBを壊す | 既存の表の件数や列が変わる | 書き込む SQL は C だけが実行する。既存の表は変えない（N-02） |
| `.env` や接続情報を Public のリポジトリに上げる | Sourcetree のステージに `.env` が出る | commit の前に、ステージしたファイルの一覧を目で見る。上げてしまったら、すぐ PM に知らせてパスワードを変えてもらう |

## いつも守ること
- **1つのPRは、1つの目的にする。** mainへの直pushはしない（Issueの運用は下記）
- **スキーマを変えたらADRに1行足す。** 手元のDBの作り直しが必要なときは、PR本文にその手順を書く
- **自分のPRは自分でマージしない。** PMのPRは他のメンバーのいずれかがレビューしてマージする
- **文書に無い機能は作らない。** 気づいたら「仕様に書かれていません」と止めてADRを切る
- 完了報告には証拠（テスト結果・ログ・スクショのパス）を添える
- **決めたことはADR.mdに1行足し、同じPRの中で下流の文書にも落とす。**（下の「ADRを足したときの手順」）
- `.env`／APIキーはコミットしない

## Issueの運用（ADR-0003）
Issueは任意（ADR-0004）。立てたときは、次を書く
タスクはGitHubのIssueで管理する。**実装計画.mdは日程と全体像の正本**で、Issueと二重管理にしない
（このファイルの状態欄は週に1回まとめて更新する程度でよい）。

| | 誰が | 何を |
|---|---|---|
| 親Issue | いでっち | 担当領域ごとに立てる（例：`[Front] 画面の実装`／`[Data] 検索ロジックの実装`） |
| SubIssue | 各担当者 | 親Issueの下に、自分の担当分を1機能＝1Issueで立てる |

Issueに必ず書くこと（レビューで確認する）:

- **根拠**：要件ID（F-xx・N-xx）／テストID（A・S・I・U）／関連ADR番号
- **完了条件**：どうなったら閉じてよいか。証拠（テスト結果・スクショ）のパスを含める
- **実装計画のタスク番号**（2-3b など）。どの計画行に対応するかを1行書く

**方式を自分で決めたときは、Issueのコメントに理由を残してからADRに1行足す。**
「担当者が提案 → PMが承認」で決めるものは、提案と承認のやり取りをIssueに残す。

## ADRを足したときの手順

**ADRだけ足して下流の文書が古いままだと、次に触った人が「文書どおりに」直して機能を壊す。**

ADRを1本足したら、**ADR.mdの「影響」欄に次の4つすべてについて書く。** 関係ないものは
「要件：なし」と明示的に書く。空欄は「まだ確認していない」と区別がつかないため使わない。

| 落とす先 | 影響欄に書くこと |
|---|---|
| 要件.md | 優先度（Must/Should/Could/Won't）や受入基準が変わるか。要件IDを消すなら「旧F-XX」の注記を残す |
| 仕様.md | 画面・入出力・テーブル定義のどこが変わるか |
| 設計.md | ファイル構成・処理の流れのどこが変わるか |
| テスト設計.md | その決定を守るテストID。無ければ足す |

古いADRを上書きする決定のときは、**上書きされる側のADRの「影響」欄にも1文追記する**
（例：ADR-0005に「○○の部分はADR-0012が上書き」）。読む人はどちらから辿るか分からないため。

### PRレビューでの確認
レビュー観点（前述の2点）に加えて、**ADR.mdに差分があるPRでは、影響欄の4項目が埋まっていて、
そのとおりに下流の文書も直っているかを見る。** ADR.mdだけが変わっているPRは差し戻す。
